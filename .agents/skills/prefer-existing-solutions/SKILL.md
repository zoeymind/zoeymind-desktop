# 先找现成的，再谈自造

**根源原则：使用已有的东西。** 用户最担心的失败模式是——agent 顺着他的想法一路死磕，把每个决策搞得很细，却没先问"这东西是不是已经有人做好了，而且想得比我更周到"。你的知识落后于真实技术迭代（AI 提效让技术飞快演进），所以**必须实时搜索验证**，不能凭记忆下结论。

## 何时触发（设计早期，不是编码后）

任何以下情况，**在拆细决策 / grill 细节 / 动手实现之前**先跑本流程：

- 用户说"我想做一个 X" / "帮我实现 Y" / 描述了一套自定义方案
- 新功能、大 feature、架构选型、引入新能力
- 你正准备开始逐个 grill 实现细节 —— **停**，先搜。
- **读/grep/审查现有代码时**，看到一段手写实现（重试、缓存、鉴权、状态机、日期处理、权限判定、队列、schema 校验等），第一反应是"现有技术栈的某个库/插件是不是已经原生支持这个？" —— 顺手核实，别默认它必须手写。
- **沟通/设计阶段 grep 到现有实现时（尤其与"用户要实现的功能"相关的代码）**：不只"读懂它在干什么"，还要**双向对比**——拿现有实现和 Context7/gh 的最新能力对照，主动判断：① 库有没有出了更新更好的功能，我们没用上？② 我们的实现是不是已经落后 / 有已知问题 / 被官方废弃的用法？**优先级排序**：与本次要实现的功能相关的现有代码最该对比（因为要在它上面改/扩，落后就直接拖累新功能）；无关代码顺带发现即可，不喧宾夺主。把对比结论告诉用户，而不是默默接受现状。

## 强制动作（拿证据，不凭记忆）

**闸门（最高优先级，不可跳过）**：涉及任何库/框架/插件的功能——"要不要自造 / 用哪个方案 / 这库支不支持 X / 现有实现落后了吗"——结论**落定前 Context7 必调**（查该库最新能力），并在回答里引用结果。**Context7 是强制项，不可跳过、不可用别的替代**；gh CLI 是可选补充（查开源实现，需要时才调）。没调 Context7 就下结论 = 违规。理由：与用户沟通设计时，他要的就是"基于最新文档"的判断，你的知识落后于真实迭代，凭记忆答等于误导。读 `node_modules/dist` 源码验证已装版本是很好的补充，但**不能替代** Context7（前者只知道锁定版本现状，后者才知道该库是否已出更新更好的能力）；文档与源码冲突时，以锁定版本源码为准。

每次给选型/自造/"库能不能做/现有实现是否落后"的结论前自问：**我这次调 Context7 了吗？** 没有就先调，再答。（纯业务逻辑、不涉及任何库能力的问题除外。）

### 1. Context7 MCP — 查库/框架/插件的最新能力

先确认现有技术栈里的库**是否已原生支持**用户想要的东西（本仓库常见：Better Auth、Prisma、tRPC、Hono、Tailwind、shadcn、Yjs/Hocuspocus、BullMQ）。

```
# 解析库 ID
写 JSON 到 xd://mcp__context_resolve_library_id: {"query":"<需求>","libraryName":"<库名>"}
# 查具体能力
写 JSON 到 xd://mcp__context_query_docs: {"libraryId":"/org/project","query":"<能不能做 X，怎么做>"}
```

真实案例：用户要"项目级 RBAC 自定义角色"，Context7 查出 Better Auth `dynamicAccessControl` 原生支持运行时建角色 + 存 DB + 防提权 —— 一半的活不用自己造。**这就是本 skill 的价值。**

### 2. GitHub CLI — 找开源实现 / 代码片段 / 可嵌入的子产品

现有技术栈的官方插件不够时，搜开源项目：有没有人做了同类产品，实现比用户想的更完整。

```bash
# 搜仓库（按 stars/活跃度）
xd://github { "op":"search_repos", "query":"<关键词> language:typescript stars:>500" }
# 搜代码实现片段
xd://github { "op":"search_code", "query":"<具体 API/模式>" }
```

真实案例：用户要"API 测试模块"，先搜 Apifox/Postman/Hoppscotch 的开源实现 —— 二次开发或直接嵌入，比从零写 HTTP runner + 断言引擎省 10 倍。

### 3. 评估维度

对找到的候选，看：维护状态、最近 commit、stars、license、与现有栈兼容性、可嵌入性、数据模型可控性。

## 审查现有代码：主动揪出造的轮子

读代码不是只理解它在干什么，还要判断**它本不该自己写**。看到手写实现时：

1. 识别这段代码在解决什么通用问题（重试退避、LRU 缓存、JWT 校验、cron 调度、权限矩阵、状态机、CRDT、日期/时区、表单校验、文件上传……）。
2. 用 Context7 查现有技术栈的库是否已原生支持（先查已装的：Better Auth / Prisma / tRPC / Hono / Zod / BullMQ / Yjs / date-fns 等），必要时用 gh CLI 搜是否有成熟小库。
3. 若确认造了轮子 → **主动指出**，附证据：
   > "这段 `<文件:行>` 手写了 `<功能>`，但 `<已装的库>` 原生支持（文档链接）。手写版还缺 `<边界/bug>`。建议换成库调用。"
4. 不确定就说不确定，别硬安现成方案；但**别默认手写就是对的** —— 手写往往是当初不知道有现成方案，不是深思熟虑的选择。

这条对 review、重构、diagnosing-bugs 尤其重要：很多 bug 的根因就是手写了一个库早已正确实现的东西（边界没处理、并发没锁、时区没转）。

## 输出：说服，而非顺从

搜完后**主动给结论 + 立场**，不要默默顺着用户的自造想法走：

- **能一键用现成的** → "你不用死磕这些细节，`<库/插件>` 已经原生支持，直接启用即可，理由 + 官方文档链接。我强烈建议用它而不是自造。"
- **能二次开发现成的** → "从零写要处理 A/B/C，`<开源项目>` 已经做好了，二次开发/嵌入更省，它甚至考虑了你没想到的 D。"
- **确实要自造** → "搜了官方插件 + GitHub top N + 社区，没有合适现成实现（附搜索过程），因此建议自建，这里是最接近的参考实现供借鉴。"

每条结论**必须附来源**（Context7 文档 / GitHub repo URL / 代码片段）。无证据不下结论。

## 红线

- NEVER 凭记忆断言"某库不支持 X" —— 先 Context7 查。知识落后是默认前提。
- NEVER 用户一说想法就开始逐个 grill 实现细节 —— 先搜现成方案，很多细节现成的已经替你决定了。
- NEVER 因为"自己写更可控"就跳过搜索 —— 先看现成的，再决定值不值得自造。
- 找到更好的现成方案时，有义务说服用户改用，即使这和他初始想法冲突（对齐 CLAUDE.md：有明确授权质疑用户假设与选型）。
- NEVER 读到手写实现就默认它是深思熟虑的选择 —— 它常常只是当初不知道有现成方案。看到就核实。
